# reSpeaker Clip HTTPS 上传首版方案

> 日期：2026-09-20
>
> 开发分支：`experiment/https-upload`
>
> 基线：空间优化提交 `55ef94c`
>
> 状态：最小验证版已进入实现；设备实测未开始（暂无样机）。构建结果单独记录，不能视为验收通过。操作入口见 [测试说明](../tools/https_poc/README.md)。

## 1. 首版目标和范围

验证设备能否在保留现有录音能力的前提下，连接一个已配置 Wi-Fi，通过带完整服务器证书校验的 HTTPS，将一个已完成录音片段直接上传至自有服务器。

成功标准是：真实设备完成联网、TLS 握手、文件发送及服务端持久保存，双方核对长度和 SHA-256 一致，并取得资源峰值数据。编译通过、握手成功或 HTTP 返回 2xx，均不能单独代表首版验收完成。

| 首版包含 | 后续版本实现 |
|---|---|
| 单个 Wi-Fi、单个 HTTPS 服务地址 | 多网络选择、完整 App 配网 |
| AT 命令手动触发一次设备直传 | 开机自动上传、周期同步 |
| 单个已封口片段、固定长度流式发送 | 多文件持久队列、断点续传 |
| 错误反馈、取消、手动重试 | 自动退避重试、掉电恢复 |
| 停止录音后上传，上传时禁止开始录音 | 录音与上传并发、录音优先调度 |
| TLS 证书验证、设备令牌认证 | 凭据轮换、双向 TLS 等扩展 |
| 保留本地原始文件 | 上传确认后自动清理 |

此版本是“设备主动执行上传”的技术验证，操作由测试者发命令触发；不宣称已经实现无人工操作的自动同步。只使用非敏感测试音频，不把 HTTPS 传输加密等同于本地录音加密。

## 2. 开发隔离与前置条件

空间优化分支保留在 `55ef94c`，HTTPS 的代码和配置只进入新分支。实施时为两个分支建立独立工作目录和服务器源码目录，构建分别使用 `build-clip-ext-patch` 与 `build-clip-https`。共用 NCS／工具链，原则上不修改共用 SDK；若必须修改，先隔离该依赖。

HTTPS 构建始终记录实际源码提交及未提交差异，不能把实验构建覆盖到已验收的空间优化产物目录。

硬件测试前必须先通过外置补丁验证：迁移／重建缩小后的 LittleFS，将匹配的补丁写入 SPI3 Flash 并回读校验，确认冷启动及 Wi-Fi 启停正常。HTTPS 开发和编译可先进行，但不能用未写入补丁的设备判断 TLS 方案失败。

当前应用资源基线：Flash 已用 844,044 B，余 89,332 B；静态 RAM 430,914 B。运行时可用堆及 TLS 峰值尚未知。BLE 默认保留；新增功能放不下时先量化各模块增量，再决定裁剪。

## 3. 设备与服务端路径

测试者通过现有 AT 控制通道设置试验配置和时间，指定片段并触发任务。设备独立执行：

**检查片段与设备状态 → 获取存储使用权 → 计算哈希 → Station 联网／DHCP → DNS → TLS → HTTPS PUT → 校验保存回执 → 释放资源。**

服务端执行：认证设备 → 流式接收临时文件 → 校验长度／哈希 → 持久提交 → 返回回执。首版不接 ASR、LLM、对象存储和长期记忆，先将接收文件保存到验证服务器本地受控目录。

### 3.1 设备模块划分

| 模块 | 修改／新增位置 | 责任 |
|---|---|---|
| 实验开关及构建配置 | 应用 Kconfig、独立 HTTPS 配置片段、CMake | 可选择加入 Station、TCP、TLS、HTTP；记录各步骤资源增量 |
| Wi-Fi Station | `wifi_station.c`、`https_poc.h` | 联网、DHCP 就绪、断连事件和接口关闭；ready 回调及共存配置 |
| TLS／HTTP 与任务管理 | `https_poc.c/.h` | 首版合并为单任务模块；证书校验、流式发送、状态、取消和资源回收 |
| TLS 分配器适配 | `tls_allocator.c`、CMake | 仅当前应用镜像替换 NCS 独立堆初始化，TLS 使用现有系统堆；不修改共享 SDK |
| 文件读取与占用 | 复用 `storage.c/.h`，集成 `clip_event.c` | 定位封口片段、持有读取使用权、防止空闲断电与删除冲突 |
| 控制与状态集成 | `at_commands.c`、`clip_event.c/.h` | 任务触发／查询／取消、互斥与状态通知 |
| 验证服务 | `tools/https_poc/` | TLS 入口、认证、文件校验、持久保存、回执、自动化测试及控制脚本 |

首版实验构建优先只编入 Station 业务路径，原 AP 模式继续由空间优化分支验证。HTTPS 版本中现有 AP 命令应明确返回不支持，不能悄悄改成另一种行为。先测量所需驱动依赖，再决定哪些 AP 配置可关闭；不能仅按配置名称删掉 Station 需要的公共组件。

### 3.2 任务状态与互斥

拟定状态：`IDLE → PREPARING → CONNECTING → TLS → SENDING → VERIFYING → SUCCEEDED`；任意活动状态可进入 `FAILED` 或 `CANCELLED`，清理完成后才允许下一个任务。

- 主线程统一授予任务使用权并处理状态转换，耗时联网／哈希／上传放在独立工作线程，不阻塞 AT 或主事件循环。
- 只有停止录音、无暂停中的录音会话、无其他传输、无 OTA、无 USB 存储独占时接受上传。
- 上传期间拒绝录音启动、删除目标文件、格式化、其他文件传输和 OTA 等冲突操作，返回明确 `BUSY`。首版不自动中断上传来开始录音。
- 任务接受后即持有存储使用权，直到文件句柄关闭、工作线程完成清理后释放。将其纳入现有 SD busy 判断，避免空闲关电；短时重新挂载不能代替全程占用。
- 状态检查和占用必须同步完成，避免录音启动与上传申请同时通过。取消通过线程可见的标志及有界网络等待实现，不由另一个线程直接释放仍在使用的 TLS 或文件对象。
- 上传中关机请求先取消任务并返回忙；清理后需要再次发起关机。意外掉电按“服务器可能收到部分数据、设备原文件仍保留”处理。

## 4. 测试配置、时间和 TLS

已新增 `AT+NETCFG=ssid,password`、`AT+UPLOADCFG=host,port,device,token`、`AT+UPTIME=Unix秒`、`AT+UPLOAD=<session_id>:<正整数片段号>`、`AT+UPLOAD?`、`AT+UPLOADCANCEL`。均限定 USB，配置仅存在 RAM。上传响应表示受理，必须继续查询最终状态。

首版通过受控 USB 测试连接注入 Wi-Fi 密码和设备令牌，仅保存在 RAM，重启后重新配置，不把凭据编译进镜像、保存到日志或纳入 Git。若通过 BLE 暴露这些命令，需要已有绑定认证，并验证其权限；默认先限定敏感配置为 USB。公有 CA 或测试 CA 证书可以作为构建资产保存。

`AT+UPTIME` 单独设置 `CLOCK_REALTIME`，不依赖原 `AT+TIME` 的录音命名时钟。TLS 编译开启 `MBEDTLS_HAVE_TIME_DATE`；必须实机验证错误时间／过期证书被拒绝。首版由测试电脑注入可信时间；时间未就绪或明显非法时拒绝上传。重启重新注入；SNTP 和长期时钟维护留到后续版本。

首版固定 HTTPS 域名、端口及受控证书链，要求链验证、有效期和主机名验证全部开启，发送正确 SNI。使用当前 SDK 提供的 TLS socket／HTTP 客户端，首选验证 TLS 1.2 的一个双方支持的安全套件；最终套件和证书算法按实际 SDK 构建配置记录，不预设不存在的 Kconfig 项。

无 HTTPS 降级、无跳过证书检查、无自动跨域重定向。设备令牌通过 `Authorization` 头发送，服务端把令牌绑定到设备身份，不能仅相信 URL 中的设备 ID。配置查询不返回密码或完整令牌。

## 5. 最小上传协议

采用固定长度二进制请求体，避免 multipart 和整文件内存缓存。应用读文件时按小块发送，但 HTTP 请求本身仍是一整个文件；不实现 HTTP 分块编码或应用层断点续传。

```http
PUT /v1/devices/{device_id}/recordings/{session_id}/{segment_id}
Authorization: Bearer <device_token>
Content-Type: application/octet-stream
Content-Length: <file_size>
X-Content-SHA256: <64位十六进制哈希>
```

设备只接受已有会话与片段标识，由存储模块定位文件，不允许 AT 参数指定任意路径。服务端也验证标识并生成存储路径，拒绝路径穿越和身份不匹配。

片段原始字节原样传输，首版不转换 WAV／Ogg。设备先在已占用且不可变的文件上流式计算 SHA-256，再从头流式发送；该过程增加一次 SD 读取，换取明确的校验协议。

首次持久保存返回 `201`；同一设备／会话／片段、长度和哈希完全一致时返回 `200`，不重复建立对象；同一标识对应不同内容时返回 `409`。示例回执：

```json
{"status":"stored","object_id":"opaque-id","size":240000,"sha256":"<64位哈希>"}
```

设备须同时验证允许的状态码、完整响应体、`status`、长度和哈希，才能记录本次成功。错误的回执或截断响应均失败。成功后只报告结果，不更新现有手机同步计数，不删除本地片段。

首版限制：单文件最大 8 MiB，响应体最多 1 KiB，响应头总量限制 4 KiB，单任务单连接，禁用压缩和重定向。这些是试验边界，可根据实际片段大小调整；超限在读取／解析阶段明确拒绝。

服务端按声明长度流式写临时文件并自行计算哈希，验证一致后同步内容、原子发布最终对象并持久化目录变化，再返回成功。相同 ID 并发请求需串行化；重启后能从最终对象核对幂等结果。中途断开的临时文件不能成为最终录音，过期清理；设备收到超时可用同一 ID 重传整文件。

## 6. 资源、超时与错误处理

| 项目 | 首轮设计值／策略 |
|---|---|
| 文件发送缓冲 | 2 KiB，固定上限，处理短读／短写 |
| 并发 | 1 个任务、1 个 TLS 连接；不并发录音 |
| TLS 内存 | 与现有业务共用 80 KiB 系统堆；上传缓冲也按任务分配；静态可链接不代表动态峰值足够 |
| 网络等待 | 联网／DHCP 30 秒，DNS 配置 5 秒，连接及 TLS 30 秒 |
| 发送接收 | 无进展 15 秒超时，整任务目标 300 秒；取消会关闭底层连接，DNS／驱动调用的退出延迟须实测 |
| 响应内存 | 有界解析；不能随远端 Content-Length 任意分配 |
| 重试 | 首版不自动重试，查询失败原因后人工重试 |

上述超时是初始配置目标，非已测指标。实现时检查 SDK 的 DNS、socket 和 TLS 调用能否遵守超时与取消边界；必要时用可轮询的等待方式，不通过无限等待掩盖问题。

错误分类至少包括：状态冲突、文件无效、补丁／Wi-Fi 初始化失败、连接失败、无 IP、DNS 失败、时间无效、证书失败、认证失败、资源不足、网络中断、服务器拒绝、回执不匹配及取消。所有出口都应关闭连接／文件、释放缓冲及存储占用，恢复到可录音状态。

提供 `https-measure.conf` 开启堆统计和线程栈水位基础能力；完整采样输出与冷握手峰值测量仍须样机联调补齐。测量版与 Production 版分别构建，说明观测工具自身占用；不把静态 RAM 减少当成运行时余量增加。

## 7. 实施顺序与交付

| 步骤 | 开发和验证内容 | 交付／通过条件 |
|---|---|---|
| H0 | 建立独立工作目录及构建；准备 TLS 接收服务和测试证书 | 基线可复现，电脑客户端可验证认证、校验及重复提交 |
| H1 | Station、DHCP、DNS、时间注入 | 样机稳定取得 IP 并解析目标域名，失败后仍可录音 |
| H2 | TLS＋小型健康检查请求 | 正确证书成功，错误主机名／CA／时间失败；取得峰值资源数据 |
| H3 | 单片段 PUT、回执验证、任务互斥及取消 | 文件完整保存，双方哈希一致，原文件保留 |
| H4 | 异常测试、重复连接和资源对比 | 无泄漏或状态卡死，形成验证报告和可重复脚本 |

每步单独记录相对 `55ef94c` 的 Flash/RAM 增量及功能取舍。构建超限时先检查新增协议和密码算法配置，测量后逐项优化；不关闭证书校验、不盲目压缩录音缓冲。若保留核心录音能力后仍无法通过 TLS，停止扩展功能并报告资源缺口。

首版交付包括：固件源码及配置、接收服务和部署说明、测试证书生成方法、控制与验收脚本、构建产物、资源／功能报告。私钥与令牌留在受控测试环境，不纳入交付源码仓库。服务端搭建在隔离目录和专用端口，部署前检查现有服务，避免覆盖。

## 8. 验收清单

- 传输至少 3 种大小的片段（小片段、实际常见片段、8 MiB 边界文件），每份服务器长度／SHA-256 与设备一致；实际录音还应核对可解码性。
- 连续执行至少 20 次冷 TLS 连接及上传，记录堆／栈变化；不能只测试连接复用。
- 验证错误 CA、错误主机名、过期证书／错误时间、401、409、413、500、错误哈希回执、截断响应和超大响应。
- 上传中断网、服务端断开、主动取消，以及响应丢失后重复上传，均可退出并重新操作；失败时本地文件不变。
- 上传期间尝试开始录音、删除目标片段、开启 AP、进入 OTA，验证互斥；结束／失败／取消后完成至少 10 次录音与上传交替测试。
- 让任务停顿超过 SD 空闲断电阈值，验证存储使用权有效；检查网络等待没有长时间持有存储内部锁。
- 设备与服务器重启后，确认已完成文件仍存在，未完成文件不被误报成功；不要求设备自动续传。
- 独立记录外置补丁写入及启动验证结果；HTTPS 结果必须来自该前置验证通过的样机。

## 9. 与后续版本的衔接

首版通过后，第二版在同一设备身份、片段 ID 和幂等提交规则上增加持久队列、自动联网／补传、凭据保存及断点协议；再增加录音上传并发与确认后清理。历史录音加密需要单独验收，并重新测量加入后的资源峰值。

首版设计保留这些扩展位置，但不提前实现完整云端管理、AI 或手机中继，以便尽快回答核心问题：**现有硬件在实际资源约束下，能否可靠完成带证书校验的 HTTPS 文件直传。**
